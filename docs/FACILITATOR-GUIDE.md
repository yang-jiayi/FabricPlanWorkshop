# 講師向け進行ガイド：導入検討につなげる180分

このガイドは、日本のお客様10〜20名を対象に、Fabric Planning の価値と導入条件を体験で確かめるための進行案です。機能を一通り紹介することよりも、**「自社のどの計画業務から試すか」を決めること**を重視します。時間配分と運営体制は本教材の提案であり、Microsoft の製品要件ではありません。

## 終了時に持ち帰るもの

参加者は、次の4点を説明できることを目指します。

1. 全社目標を配賦し、現場の入力と承認をつなぐと、どの受け渡しを減らせるか。
2. 実績、計画、見通しを区別し、入力変更がどこに反映されるか。
3. 計画を Fabric SQL に保存すると、後続の分析でどう利用できるか。
4. 自社で試す業務、データ、関係者、成功条件、費用確認の担当を決められるか。

## 推奨する運営

**講師が設計と設定を行い、参加者が入力,レビュー,承認を体験する形式**を基本にします。最初から全員にアイテム作成を求めると、権限、時間、課金の負担が増えるためです。作成方法の習得を目的とする場合は、別枠の実装者向け演習にします。

10名なら5組、20名なら10組のペアを作ります。片方が操作し、もう片方が数値の前提を確認する役を担当し、途中で交代します。ログイン,入力する人はそれぞれのアカウントを使用し、アカウントは共有しません。10名では講師1名＋補助1名、20名では講師1名＋補助2名を目安にしてください。

2段階の承認まで体験する場合は、ペアの2人を申請者と地域承認者に分け、講師が本社承認者を担当する構成を提案します。申請状態の列と、地域,本社の承認2列を分け、3つの別IDで事前に試してください。ペアだけで申請,承認を試す構成は、承認1段階の体験として範囲を明示します。[Lab02の設定と確認事項](../labs/02-allocation-and-collaboration.md#パート4承認を依頼する)に従い、通知を含めて実施した範囲だけを記録します。

| 役割 | 担当すること |
|---|---|
| 講師 / FP&A責任者役 | 全体の目標、設計のデモ、承認の説明、時間管理 |
| 参加者 / 地域担当者役 | 指定された地域,製品の計画入力、前提のコメント、変更結果の確認 |
| 参加者 / レビュー担当者役 | 入力前後の数字を記録し、目標と現場見通しの違いを説明 |
| 補助講師 | サインイン、接続、権限の切り分けと、遅れた参加者の復帰支援 |

全員で同じセルを同時編集しないでください。ペアごとに対象地域,製品,時間帯を割り当てます。共有シートでの競合を避けるための運営上の割り当ては、セキュリティによるアクセス制御とは区別して説明します。

**入力中心の開催では、原典ラボの全手順を参加者が実行するわけではありません。** 計画シート,入力列,予測,シナリオの作成、設計やロックの設定、書き戻し先の設定は講師が事前に行い、当日はデモで説明します。参加者は準備済みの末端セルへの入力、コメント、承認、結果の確認を担当します。全社合計の変更、トップダウン配賦、ロックの変更、Optimizer の実行は講師だけが行い、他の参加者はその間に入力しません。全員が設計まで操作する開催に変更する場合は、Planner 前提の費用と時間に切り替えます。

## 開催前の確認

### 1週間前：管理者と環境を確認する

- [モジュール00](../labs/00-prerequisites.md)に沿って、容量、テナント設定、モデルの Read / Build、Plan アイテムの共有、書き戻しの権限を確認します。
- モジュール09を別枠で実施する場合は、有料F2以上またはFabric有効化済みP1以上の容量、Data Agent / Tenant AIの設定、クロスジオ処理の方針、Ontology Previewの提供状況を管理者と確認します。Lab04由来のForecastとモデル値を突合したSnapshotを事前準備し、検証できない書き戻し履歴を「最新」と推測しません。サンプルルートの実機確認では、Lakehouse FilesのCSVをWarehouseへCOPYする際にCREDENTIAL句なしのEntraパススルーが使われ、Workspace Identityを指定した経路は失敗しました。Workspace Identityは必須要件とせず、組織で承認された認証 / 権限だけを使います。
- B2B ゲストを使う場合は、実際に使う参加者IDでサインインから入力まで試します。「全員社内アカウントでの確認」をゲスト参加の動作確認に代用しません。
- 作成担当は演習用ワークスペースで Member / Admin を基本とし、参加者は必要な操作ができる権限に限定します。課金ロールはワークスペースの役割名とは別で、操作により変わります。
- 公式資料には、メタデータを SQL に保存する説明と、新しい Plan では OneLake に保存する説明が併存しています。新規作成時に何ができるかを実環境で確認し、旧画面の手順を全員へ要求しません。
- 試用容量のデータベース上限、既存アイテム数、計画シート数、作成予定の SQL 書き戻し先を棚卸しします。不要かどうか不明なアイテムを削除して枠を空ける運用はしません。
- 本番ワークスペース、顧客の実データ、実運用の承認ルートは使いません。

### 2〜3日前：講師が通しで実施する

- この教材と同じサンプルを用意し、[01](../labs/01-environment-and-first-sheet.md)→[02](../labs/02-allocation-and-collaboration.md)→[03](../labs/03-optimizer.md)→[04](../labs/04-forecast-and-writeback.md)→[06](../labs/06-intelligence-canvas.md)を実行します。
- 実画面の UI 名、対象モデル、日付階層、値の表示単位を記録します。日本語 UI の表記が異なる場合は、教材の英語識別子との対応を配布します。
- 次の復帰地点を用意します。A：モデル接続済み、B：配賦と入力列が準備済み、C：予測作成済み、D：書き戻しとライブ KPI が検証済み。準備方法の正式なサポート状況を確認し、複製で接続,承認,書き戻し設定が引き継がれると決めつけません。
- 別の参加者IDで、閲覧,入力,承認,書き戻しをそれぞれ確認します。権限のないユーザーから行や操作が見えないことも確認します。
- Capacity Metrics と SQL の消費を確認し、想定人数で試験します。F2 を人数の推奨容量として提示しません。
- 講師の画面と、成功時の保存値,ログ,スクリーンショットを用意します。録画や画面共有に切り替えた場合は「参加者の操作完了」と数えません。

### 前日〜開始直前

- 参加者へサインイン確認、ブラウザー、演習用URL、データの取り扱い、費用を負担するテナントを案内します。
- 補助講師へペア番号と担当範囲を渡します。接続エラーを参加者全員で同時に追いかけず、補助講師が切り分けます。
- 課金セッションが始まる操作と、途中終了できないことを責任者と確認します。演習終了後のアイテム削除,容量停止でセッション料金がなくなるとは案内しません。

## 当日の進行：合計180分

| 経過時間 | 時間 | 内容 | 参加者が確認すること |
|---|---|---|---|
| 0〜10分 | 10分 | 課題の共有とゴール | 自社で困っている集計,調整を1つ挙げる |
| 10〜25分 | 15分 | 00 / 01：権限,課金の要点と準備済み環境の確認 | 指定アカウントでモデルとシートを開ける |
| 25〜35分 | 10分 | 01：既存レポートから現在地を見る | FY25実績とFY26目標を区別できる |
| 35〜60分 | 25分 | 02：配賦、現場入力、コメント,承認 | 配賦後の合計が目標に一致し、ロック対象の値が変わらない |
| 60〜75分 | 15分 | 03：Optimizer の講師デモ＋ペア確認 | 目標を満たす入力が、業務上妥当か判断する |
| 75〜85分 | 10分 | 休憩 | 補助講師が遅れを確認する |
| 85〜110分 | 25分 | 04：見通しと書き戻し | 成功ログとSQLの値を照合する |
| 110〜130分 | 20分 | 06：入力とキャンバスの連動 | 1セルの変更が対応するライブKPIへ反映される |
| 130〜145分 | 15分 | 08：容量,ガバナンス | 自社の参加人数,操作,権限に置き換える |
| 145〜160分 | 15分 | 導入検討シートの記入 | PoCの対象、担当者、成功条件を決める |
| 160〜180分 | 20分 | 質問,復帰,まとめの予備時間 | 未解決事項を担当,期限付きで残す |

環境作成のすべてを当日全員で行う時間配分ではありません。05のメジャー / 行モデルの詳細、07のPowerTable、CubeやInfobridgeは、目的に応じた発展回か短い講師デモに分けます。特に05の未解決の損益集計を、顧客向け本編の成功判定には使いません。

## 発展編：モジュール09（追加45〜60分）

モジュール09は**既存の180分本編に含めない別枠**です。モジュール04で使ったProduct × 月のGross RevenueとForecastを同一Scenario / Plan versionで照合し、UTF-8 CSVをLakehouse Filesへ一時配置します。Warehouseは明示型Stageと独立した数値検算に使い、Ontology / GraphはLakehouseの管理Deltaテーブルにバインドします。件数 / キー / 値を検査してからOntology Previewと読み取り専用Fabric Data Agentを設定します。データ準備時間は45〜60分の目安に含みません。**実機で確認したのは合成CSVを使うPart 3〜5です。実Plan / writebackからの抽出を含むEnd-to-End確認ではありません。** AgentのQ1 / Q3 / Q4cは合成値で検算済みですが、Q4 / Q4aは`SQLCandidatesFailedFilterError`となり原因未特定です。実機確認と未確認事項の一覧は[Lab09](../labs/09-variance-analyst.md)を参照してください。

開始条件は、有料F2以上またはFabric有効化済みP1以上、管理者が承認したTenant AI / クロスジオ設定、Ontology Previewの利用可否、専用Warehouse / Lakehouse Filesの課金承認、実行者の承認済み読取経路とPlan / モデルへの必要な読取権限です。Workspace Identityは必須とせず、実証済みのCREDENTIAL句なしEntraパススルーも組織ポリシーと権限が許す場合に限ります。Long with Changesの完全な現行状態を証明できない場合は開始せず、承認済みの全件Snapshotを用意します。NorthwindのOpen period値を確定実績と呼ばず、Agentの回答をWarehouseの全精度値と独立照合してください。AgentはPlanを変更,承認,書き戻しできません。

手順,データ契約,検算と安全な終了は[モジュール09](../labs/09-variance-analyst.md)を使います。参加者向けに実施する場合も、テナント固有情報やデータ行を公開画面 / 録画へ含めず、本人別の権限確認を管理者アカウントの結果で代用しません。

## 体験を導入判断につなげる問い

| 体験 | 講師の問いかけ | 持ち帰る検討事項 |
|---|---|---|
| 配賦,ロック | 「確定済みの月を守りながら、目標変更をどこへ配っていますか」 | 配賦基準、ロック単位、例外処理 |
| コメント,承認 | 「この数字の前提と、最後に承認した人を今はどう探していますか」 | 入力者、承認者、証跡の要件 |
| Optimizer | 「目標を達成していても、実行できない組み合わせはありますか」 | 制約、調整可能なドライバー、人による最終判断 |
| 統計予測 | 「予測値を採用する前に、何と比べて妥当性を確認しますか」 | 履歴期間、季節性、誤差、説明可能性 |
| 書き戻し | 「承認済みの計画を、どのレポートや業務へ渡したいですか」 | 保存先、更新頻度、粒度、権限 |
| ライブ KPI | 「実績と計画を混同せずに、変更の影響を誰が確認しますか」 | メジャーの出所、表示単位、モデルへの反映方法 |

作業時間の削減や投資対効果を、このサンプルの操作だけで実証したとは説明しません。お客様の現状値を聞き、PoCで測定する対象にします。

## 成功判定と、つまずいた場合の進め方

| 場面 | 成功判定 | 未達の場合 |
|---|---|---|
| 接続 | 指定したモデルのデータが表示される | ID、Read / Build、テナント設定を補助講師が確認。参加者は準備済み環境か講師デモで追う |
| 配賦 | 合計が目標と一致し、ロック期間が変わらない | 対象セル、メジャー、階層、ロックを確認。やり直す前に現在値を控える |
| 最適化 | 目標と結果、制約、変えた入力を説明できる | 一致しない数値を隠さず、制約,許容誤差を確認 |
| 書き戻し | 現在の実行の成功ログと、対象シナリオ,行,値がSQLで一致する | エラーやpartial状態を残す。件数だけで成功としない。権限,宛先,書式,NULLを確認 |
| キャンバス | 対象入力を変えると、From Sheets を参照するKPIが変わる | モデル由来のメジャーを使っていないか確認。元モデルの値まで変わるとは説明しない |
| データ分離 | 別ユーザーで許可,拒否の両方を確認できる | レガシーアクセス制御と Roles & Policies、モデルのRLS、SQLの接続IDを分けて確認 |

不具合が発生したら、開始値、対象シート / シナリオ、操作、期待値、実際の結果、ログの時刻を記録します。修正後は同じ操作を再実行し、可能なら別の担当者が確認します。

## 10〜20名の費用確認

以下は公式の1セッション当たり **Planner 847 / Stakeholder 168 / Viewer 37 CU時間**を使った試算です。全員が新規セッションを始め、同じテナント,容量を使用し、**参加者とは別に講師1名がPlanner**であると仮定します。補助講師、SQL、OneLake、自動化、Infobridgeなどは含めません。金額や必要SKUを保証する表ではありません。

| 進め方 | 参加者10名＋講師1名 | 参加者20名＋講師1名 |
|---|---:|---:|
| 全員が計画シートを作成（全員Planner） | 9,317 CU時間 | 17,787 CU時間 |
| 講師が作成、参加者は入力,承認（Stakeholder） | 2,527 CU時間 | 4,207 CU時間 |
| 講師デモ、参加者は各自ログインして閲覧のみ（Viewer） | 1,217 CU時間 | 1,587 CU時間 |

計算式は `847 + 参加者数 × 各ロールの消費量` です。ペアで交代する場合も、それぞれのアカウントが行った操作でロールが決まります。途中でシート作成,設計変更などを行うと、上位ロールに変わる可能性があります。セッションの有効範囲,アップグレード,残存期間は[公式課金資料](https://learn.microsoft.com/en-us/fabric/iq/plan/resources/billing-fabric-plan)と[ロール説明](https://learn.microsoft.com/en-us/fabric/iq/plan/overview-roles)で確認してください。

公式課金例は「30日（730時間）」と記載しています。暦上の30日は720時間ですが、この教材は公式の計算前提を勝手に置き換えません。実際の期限と請求は管理画面で確認してください。少人数の製品最小容量から、20名分の体感速度や総費用を推定しないでください。

## 導入検討シート

145〜160分の15分間で、各社から1件を選びます。

| 項目 | 記入すること |
|---|---|
| 最初に試す業務 | 例：月次売上見通し、部門別費用予算。今回は1つに絞る |
| 今の課題 | 集計待ち、数字の不一致、承認者の確認など、具体的な状況 |
| 現状値と成功条件 | 現在の締め日数,手作業回数,差異確認時間。PoC終了時に何を測るか |
| 必要なデータ | セマンティックモデル、期間、粒度、マスター、機密区分 |
| 関係者 | 業務責任者、入力者、承認者、Fabric管理者、セキュリティ担当 |
| 検証する条件 | 接続、権限、RLS、書き戻し、容量、運用、対象地域での提供状況 |
| 次の一歩 | PoCの範囲、担当者、日程、費用確認を行う責任者 |

開催後は、観察した成功,未達,未検証を分けて共有します。お客様への連絡,日程調整,環境の変更は、各社の担当者が合意した範囲で行ってください。
